## Executive Summary

v0.6.0 completes the **architectural redesign**: the Tick kernel is now
separated from the ReAct loop. Agents no longer block on LLM or tool
calls inside a tick — they submit Intents, enter waiting states, and are
re-activated when results arrive.

The design goal from the review:

> **ReAct is the agent's behavioral protocol; Tick is the kernel's advancement protocol. They are not 1:1.**

This is now implemented and proven end-to-end:

```text
tick t:    Agent produces Intent (SubmitLLMRequest / SubmitToolRequest)
           → PendingOperationRegistry → WAITING_FOR_LLM / WAITING_FOR_TOOL
tick t+1:  FakeProvider completes op → Ingest delivers → agent re-activated
           → parses result → produces next Intent
```

**Label:** `v0.6.0 — Async LLM/tool runtime with continuation-based agents`

## What Changed

### 1. Agent decide() Produces Intents (`agent_runtime.py`, `llm_agent.py`)

**Before:** `decide(observation) -> ActionPlan` — rule-based agents
returned action lists; LLMAgent blocked on the model call inside the tick.

**After:** `decide_intents(observation, continuation) -> list[Intent]`

- `AgentRuntime` protocol extended with `decide_intents()`
- `BaseAgent.decide_intents()` default: converts `decide()`'s ActionPlan → Intents (backward-compatible bridge for rule-based agents)
- `action_plan_to_intents()` converter: delegate → DelegateIntent, send_email → SendEmailIntent, write → WritePrivateFileIntent, read/ls → SubmitToolRequest, complete_task → CompleteTaskIntent, fail_task → FailTaskIntent
- `LLMAgent.decide_intents()` **never blocks**:
  - Continuation has pending result → parse LLM response into Intents
  - Otherwise → `SubmitLLMRequest` (async)

### 2. Continuation-Based Agent State (`models/continuation.py`)

Each agent holds an `AgentContinuation` in `AgentRuntimeState`:

```text
phase: fresh | waiting_for_llm | waiting_for_tool | processing_result | ...
pending_request_id, react_turn, total_llm_calls, total_tool_calls
last_llm_result, last_tool_result
event_log (audit trail of the ReAct cycle)
```

Lifecycle across ticks:

```text
READY → PROCESSING → WAITING_FOR_LLM → (result arrives) → READY
→ PROCESSING → WAITING_FOR_TOOL → (result arrives) → READY → ...
```

Key additions:
- `receive_llm_result()` / `receive_tool_result()` — delivered by `_phase_ingest`
- `finalize_result_processing()` — resets phase after agent consumes a result
- `AgentRuntimeState.begin_activation()` — resumes WAITING_* agents → PROCESSING

### 3. Async External Operations (`pending_ops.py`)

`PendingOperationRegistry` tracks all in-flight external operations:

```text
SUBMITTED → PENDING → COMPLETED / FAILED / CANCELLED / TIMED_OUT
```

Each op: request_id, agent_id, task_id, created_tick, eligible_tick,
deadline_tick, status, result, error, retry_count.

**Critical fix:** consumed ops are `remove()`d after Ingest delivers them
— otherwise they re-deliver every tick, causing duplicate effects.

### 4. 9-Phase Kernel Tick Cycle (`simulation.py`)

```text
1. Ingest    — collect completed ops, deliver to continuations, wake agents
2. Freeze    — snapshot global state
3. Schedule  — ready set from events + agent states
4. Observe   — ready agents read snapshot
5. Decide    — produce Intents (NON-BLOCKING, no sync LLM/tool)
6. Validate  — validate Intents (tool capability, delegation, payload)
7. Commit    — apply staged effects, register pending ops
8. Publish   — timeout checks, wake events
9. Audit     — record all events
```

`_phase_act` converts validated Intents:

| Intent | Handling |
|--------|----------|
| SubmitLLMRequest | register LLM_REQUEST op, agent → WAITING_FOR_LLM |
| SubmitToolRequest (read/ls) | execute synchronously (local tools) |
| SubmitToolRequest (remote) | register TOOL_REQUEST op, agent → WAITING_FOR_TOOL |
| SendEmailIntent | stage EMAIL_SEND effect |
| DelegateIntent | stage TASK_CREATE + EMAIL_SEND effects |
| WritePrivateFileIntent | stage FILE_WRITE effect |
| CompleteTaskIntent / FailTaskIntent | stage TASK_UPDATE effect |
| WaitForEventIntent | agent → waiting state |

### 5. Deterministic Fake Providers (`fake_llm.py`, new)

- **`FakeLLMProvider`** — scripted LLM responses per (agent_id, call_index), configurable latency
  - `register_script()` / `replace_script()` (dynamic injection of runtime values)
- **`FakeToolExecutor`** — scripted tool results per (agent_id, tool_name)
- Both complete pending ops via `advance(sim, current_tick)` — the E2E harness
  calls this before each `sim.run_tick()`

### 6. Task Transition Walk (`task_tree.py`)

`update_status(allow_walk=True)` walks the transition graph when the
direct transition is invalid (e.g. `assigned → completed` goes through
`accepted → in_progress → submitted`). Strict by default; `_phase_commit`
uses the walk for TASK_UPDATE effects.

## E2E Test Evidence

### Full Task Completion Roundtrip (`test_e2e_task_roundtrip.py`)

```text
tick 0:  human sends "analyze market" (deliver_at=1)
tick 1:  root wakes → SubmitLLMRequest → WAITING_FOR_LLM
tick 2:  LLM completes → root re-activated → parses delegate intent
         → task created + delegation email
tick 3:  research wakes (NEW_EMAIL) → SubmitLLMRequest → WAITING_FOR_LLM
tick 4:  LLM completes → research re-activated → writes report.md
         + sends [RESULT] email
tick 5:  root wakes ([RESULT] email) → SubmitLLMRequest → WAITING_FOR_LLM
tick 6:  LLM completes → root re-activated → completes task + replies to human
```

Verified at the end:
- Task status: **COMPLETED** (walked through intermediate states)
- Emails: delegation sent, result returned, human reply dispatched
- File: `report.md` written by research with LLM-derived content
- Agent states: both IDLE (no zombie waiting states)
- Audit log: ≥3 activations, ≥4 transaction commits

### Async Tool Flow (`test_e2e_async_tool.py`)

- Remote tool (web_search) → TOOL_REQUEST op → WAITING_FOR_TOOL
- FakeToolExecutor completes → agent re-activated → sends result email
- Tool timeout → TIMED_OUT
- Tool error → delivered to continuation
- **Hybrid flow**: LLM → tool → result (react_turn=2, 3-hop continuation)

## What This Proves vs What It Doesn't

| Proven by tests | NOT yet proven |
|-----------------|----------------|
| Async LLM submit/receive/re-activate | Real provider integration (litellm) |
| Async tool submit/receive/re-activate | Real external tool execution |
| Continuation state across ticks | Persistence across process restarts |
| Multi-hop ReAct (LLM→tool→LLM) | BoundedMicroLoop re-observation |
| Task lifecycle completion | Concurrent multi-agent LLM parallelism |
| Deterministic replay with fake providers | Real cost/latency characteristics |

## Known Limitations

### Architecture (carried from v0.5.0)

1. **Real LLM provider untested** — `llm_gateway.py` still at 51% (real litellm calls not exercised in CI)
2. **BoundedMicroLoop stale snapshot** — second round uses original snapshot, no re-observation
3. **Stale LLM response rejection** — no mechanism to discard a response for a superseded request
4. **AgentSnapshot still dict-based** — typed views (EmailView, TaskView, etc.) not yet implemented

### Transaction (P2 — next)

5. **Outbox not persisted** — emails queued in-memory; crash loses them; no idempotency
6. **SharedKB dual entry** — `SharedKB.write()` direct path still exists; KB writes not yet routed through TransactionBuffer
7. **No cross-effect rollback** — if one effect fails during application, previously committed effects in the same tick remain
8. **Task+Email consistency** — delegate stages both effects independently; partial failure leaves inconsistent state

### Async Semantics (P2/P3)

9. **Timeout → retry not wired** — ops marked TIMED_OUT but no retry mechanism or agent re-wake with error
10. **No pause at commit boundary** — pause is not yet integrated with the async model
11. **No LLM budget/rate limiting** — per-agent concurrency and cost caps not implemented

### Persistence (P3)

12. **In-memory only** — no save/load, no crash recovery, no SQLite
