## Executive Summary

v0.5.0 proves the **deterministic scripted-agent event-driven loop works across multiple ticks**. The three major deliverables:

1. **Tool handlers registered** — `read`, `write`, `ls`, `send_email`, `delegate` all go through `ToolRegistry.execute()` → handler → staged effects (writes) or direct execution (reads)
2. **`_phase_commit` implemented** — deterministic staged-effect validation, conflict resolution, and sequential application (file writes, email queueing, task creation)
3. **10 multi-tick E2E tests** proving: Root → delegate → email delivered → research activates → sends result → email delivered to root

The loop that was previously theoretical now has a tested, working implementation:

```text
Event wake → Agent activation → Decision → Tool execution
→ Pre-validation (Phase 6) → Commit-time validation (Phase 8)
→ Effect application → Event publish → Next-tick wake
```

**Important distinction — two validation phases:**

| Phase | Name | Validates | Rejects |
|-------|------|-----------|---------|
| Phase 6 | Pre-validate | `ActionPlan` | Tool not authorized, delegation target invalid, missing payload fields |
| Phase 8 | Commit-time validate | `StagedEffect` | KB permission denied, lock not held, version conflict |

Phase 6 checks intent (can the agent try this?); Phase 8 checks preconditions (is the world still consistent?).

**Label:** `v0.5.0 — Deterministic multi-tick runtime loop with staged-effect commit`

## What Changed

### 1. Tool Handlers Registered (`simulation.py`)

Five tool handlers registered in `_initialize()` via `_register_tool_handlers()`:

| Handler | Type | Behavior |
|---------|------|----------|
| `read` | Direct | Reads file from private workspace, returns content |
| `ls` | Direct | Lists directory entries in private workspace |
| `write` | Staged | Stages `FILE_WRITE` effect in TransactionBuffer |
| `send_email` | Staged | Stages `EMAIL_SEND` effect in TransactionBuffer |
| `delegate` | Staged | Stages `TASK_CREATE` + `EMAIL_SEND` effects |

Write tools stage effects that are applied in Phase 8. Read tools execute immediately.

**⚠️ Snapshot consistency concern:** `read` and `ls` currently access the live filesystem during Phase 7 (Act), not the Phase 1 (Freeze) snapshot. This means a write from Agent A in the same tick could theoretically be visible to a read from Agent B in the same tick. This violates SPEC §8.2 Freeze semantics and should be addressed in v0.6.0. See Known Limitation #1.

### 2. `_phase_commit` Implemented (`simulation.py`)

Replaced the stub with a staged-effect commit pipeline:

```text
Phase 8 — Commit pipeline:

1. Validate effects (commit-time validation):
   - Permission: only enforced for KB operations (kb_write, kb_create, kb_delete)
   - Lock: only enforced for shared KB resources (shared-kb/, project/)
   - Version: checked against current KB version

2. Resolve conflicts:
   - Same resource, same agent: keep all in effect_id order
   - Same resource, different agents: deterministic by agent_id (alphabetical)

3. Apply committed effects sequentially:
   - FILE_WRITE → write to private workspace
   - EMAIL_SEND → create email in MailSystem (deliver_at_tick = tick + latency)
   - TASK_CREATE → create task in TaskTree (status=ASSIGNED)

4. Record TRANSACTION_COMMIT audit events
```

**⚠️ Not atomic across effects.** If `TASK_CREATE` succeeds but `EMAIL_SEND` fails, the task remains created but no email is sent. There is no cross-effect rollback. This should be addressed in v0.6.0. See Known Limitation #2.

### 3. Multi-Tick E2E Tests (`tests/test_e2e_multitick.py`, new)

10 tests using the `ScriptedAgent` pattern — deterministic `(tick, ActionPlan)` injection:

| Test | What it proves |

## What These Tests Do Not Prove

The E2E tests use `ScriptedAgent` — deterministic action plans injected at specific ticks. They verify the scheduling and execution pipeline, not the LLM decision path. Specifically:

| Verified by tests | NOT verified |
|-------------------|--------------|
| Scheduler wakes correct agents | LLM prompt rendering |
| ToolRegistry dispatches to handlers | LLM provider routing |
| TransactionBuffer stages effects | ActionPlan parsing from LLM response |
| Commit applies effects | LLM timeout / retry / cancellation |
| MailSystem delivers emails | BoundedMicroLoop multi-round |
| Wake events generated correctly | Real provider cost / latency |
| Agent state transitions | Prompt injection defense |

A future "LLM E2E" test would need a `FakeLLMProvider` that returns scripted LLM responses, exercising the `LLMAgent.decide()` → `PromptTemplates` → `LLMGateway` → parse → validate path.

## Known Limitations

### Snapshot Consistency (P0)

1. **`read` and `ls` access live filesystem during Act phase** — violates SPEC §8.2 Freeze semantics. If Agent A writes a file in tick t, Agent B's read in the same tick t may or may not see it depending on execution order. The correct behavior is: both agents should see the tick t-1 snapshot. Fix: route read/ls through a frozen snapshot view in Phase 4 (Observe), or buffer writes and apply only in Phase 8 (Commit).

### Commit Atomicity (P1)

2. **No cross-effect rollback** — if `TASK_CREATE` succeeds but `EMAIL_SEND` fails in the same commit, the task remains created but no email is sent. The task owner exists but the delegate never receives the message. Similarly, `FILE_WRITE` and `EMAIL_SEND` in the same commit are independently applied. Fix: collect rollback actions during application; on failure, reverse committed in-memory effects (task removal, email dequeue).

3. **Task+Email consistency not enforced** — the `delegate` handler stages both `TASK_CREATE` and `EMAIL_SEND` as separate effects. If one is validated/rejected and the other isn't, inconsistency results. Fix: group related effects and validate them together, or use a single composite effect type.

### Shared KB (P1)

4. **SharedKB direct `write()` still exists** — not removed, just not used by the current tool handlers. Any code path that calls `shared_kb.write(...)` directly bypasses Phase 6 validation, Phase 8 commit-time validation, lock checks, version checks, and audit. Fix: rename to `_apply_committed()` (internal), add `stage_kb_write()` as the only public write API.

5. **Shared KB E2E not proven** — the commit pipeline includes KB permission, lock, and version checks, but no E2E test exercises a KB write through the full: lock acquire → read → modify → commit → version increment → wake event cycle. The `_phase_commit` applies `FILE_WRITE`, `EMAIL_SEND`, and `TASK_CREATE` — it does NOT handle `KB_WRITE` effects.

### Email Reliability (P2)

6. **No outbox persistence** — emails are queued directly to `MailSystem` during commit. If the process crashes after commit but before delivery, the email is lost. If the process crashes after delivery but before the next tick's state update, the email may be re-delivered. Fix: implement outbox with STAGED → COMMITTED → DISPATCHED lifecycle.

### LLM Integration (P2)

7. **LLM calls are synchronous** — one slow provider call blocks the entire tick. `WAITING_FOR_LLM` is modeled but unused. Fix: make LLM requests async with request ID, response correlation, timeout, and cancellation.

8. **BoundedMicroLoop uses stale snapshot** — second LLM round sees the original Phase 1 snapshot, not the results of the first round's tool calls. Fix: pass `MicroLoopObservation(base_snapshot, tool_results, staged_effects)` to each round.

### Other (P3)

9. **No persistence** — all state is in-memory. Process restart loses everything.
10. **No crash recovery** — no mechanism to resume after interruption.
11. **`ScriptedAgent` tests are not LLM tests** — they prove the pipeline, not the LLM decision path.
