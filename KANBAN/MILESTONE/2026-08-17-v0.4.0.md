## Executive Summary

v0.4.0 implements the **event-driven scheduling architecture** and **LLM integration interfaces**. The scheduler, activation models, provider gateway, executor implementations, and validate phase are present and covered by 95 new tests.

Key capabilities now wired:
- `AgentStateMachine` is the authoritative runtime state source
- `Validate` phase checks tool permissions, delegation targets, and payload fields before Act
- State transitions (IDLE → READY → PROCESSING → IDLE) tracked per activation

Remaining limitations: LLM calls are synchronous within activation, BoundedMicroLoop doesn't re-observe between rounds.

**Label:** `v0.4.0 — Event-Driven Scheduling and LLM Runtime`

## What Changed

### 1. Activation Data Models (new: `models/activation.py`)

| Model | Purpose |
|-------|---------|
| `WakeEventType` | 9 event types: NEW_EMAIL, TOOL_RESULT, CHILD_TASK_CHANGE, etc. |
| `WaitingState` | 6 granular waiting sub-states: WAITING_FOR_LLM, _TOOL, _CHILD, _MAIL, _LOCK, _HUMAN |
| `WakeCondition` | Per-agent wake condition with event_types, task_ids, resources, thread_ids, sender_ids |
| `WakeupEvent` | Event that may wake an agent, with event_id, target, tick, source |
| `ReadyCandidate` | Agent ready for activation with its triggering events |
| `AgentActivation` | Records one activation cycle (Observe→Decide→Actions→Commit) |
| `ExecutionMode` | Enum: DISCRETE_ASYNC, BOUNDED_MICRO_LOOP |
| `ExecutionConfig` | Budget limits: max_llm_calls, max_tool_calls, max_action_budget |
| `AgentWaitState` | Persistent wait state for scheduler |

### 2. State Machine Extension (`agent_state.py`)

Added 7 new states to `AgentState`:
- `READY` — agent has pending work, waiting for scheduler
- `WAITING_FOR_LLM` — LLM call in flight
- `WAITING_FOR_TOOL` — tool call in flight
- `WAITING_FOR_CHILD` — waiting for child task result
- `WAITING_FOR_MAIL` — waiting for specific email
- `WAITING_FOR_LOCK` — waiting for shared KB lock
- `WAITING_FOR_HUMAN` — waiting for human decision

Updated `TRANSITION_TABLE` with all new transitions. Added convenience methods: `wake_up()`, `wait_for_llm()`, `wait_for_tool()`, etc.

### 3. Agent Scheduler (`scheduler.py`, new)

Core event-driven scheduler with:
- **Event claiming** — explicit claim/defer/consume lifecycle (not `clear_events_for_tick`)
- **`_matches()` function** — full matching rules: event_type, task_ids, resources, thread_ids, sender_ids, wake_at_tick
- **Deterministic ordering** — sorted by agent_id
- **Max 1 activation per agent per tick**
- **Event deferral** — failed activations return events to eligible status

### 4. 10-Phase Tick Cycle (`simulation.py`)

Rewritten `run_tick()`:

```text
1. Freeze    — snapshot global state
2. Deliver   — deliver emails + generate NEW_EMAIL wake events
3. Schedule  — compute ready set from events + agent states
4. Observe   — ready agents read snapshot
5. Decide    — ready agents generate action plan
6. Act       — ready agents execute actions
7. Validate  — validate staged effects (placeholder)
8. Commit    — atomic commit
9. Publish   — generate wake events from committed effects; timeouts
10. Audit    — record all events
```

Key semantics:
- Events produced in tick t are only visible in tick t+1
- WakeCondition updates staged as effects, take effect after Commit
- Bootstrap: only agents with `metadata.bootstrap=True` wake on tick 0
- All agents woken by emails, tool results, child task changes, etc.

### 5. LLM Gateway (`llm_gateway.py`, new)

- Per-agent provider routing via profiles
- `LLMRequest` — explicit request model (no `**kwargs`)
- `LLMInvocation` — full audit trail (model, provider, tokens, cost)
- Security: API keys from env, api_base allowlist, frozen configs
- Uses litellm underneath

### 6. LLMAgent (`llm_agent.py`, new)

- Extends `BaseAgent`, overrides `decide()` to call LLM
- Integrates with `PromptTemplates` for prompt rendering
- Integrates with `LLMGateway` for provider routing

### 7. Prompt Templates (`prompt_templates.py`, new)

- System prompt generation with task/email context
- Tool definitions for function calling
- Strict `ActionPlan` parsing from LLM response

### 8. Execution Modes (`executors.py`, new)

- `DiscreteAsyncExecutor` — one activation = observe → decide → actions
- `BoundedMicroLoopExecutor` — limited LLM→Tool→LLM rounds
- `ToolInvocationRecord` — tracks tool calls with hashes (privacy)
- `ActivationResult` — activation + tool invocations + resulting state

### 9. Unified Config (`configs/agents.json`, new)

Single config file with:
- `simulation` — tick duration, delegation depth, etc.
- `execution` — mode, budgets
- `llm_profiles` — named provider configs (default, research, fast)
- `agents` — agent definitions with `llm_profile` and `bootstrap` flags

### 10. Audit Events (`audit.py`)

Added: `AGENT_ACTIVATED`, `AGENT_WOKEN`, `AGENT_IDLE`

## Known Limitations

1. **Validate phase covers tool permissions and delegation** — lock token, KB version, and conflict resolution validation are not yet implemented (require TransactionBuffer integration).
2. **LLM calls are synchronous within activation** — `WAITING_FOR_LLM` is modeled but not yet used for asynchronous provider latency.
3. **litellm required for LLM calls** — no fallback if not installed; pure rule-based simulation still works without litellm.
4. **BoundedMicroLoop doesn't re-observe between rounds** — would need fresh snapshot for true multi-round execution.
