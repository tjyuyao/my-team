## 3. What's New in v0.2.0

### 3.1 Simulation Integration Layer (`simulation.py`)

The `Simulation` class ties all subsystems together:

```python
sim = Simulation.from_config_file("configs/sample-team.json")
results = sim.run(max_ticks=10)
```

**Initialization:**
- Creates mailboxes for all agents
- Initializes private workspaces
- Registers tool permissions per agent
- Creates appropriate AgentRuntime per agent role
- Sets up HumanControl, DelegationProtocol, AuditLog

**Tick execution (7 phases):**
1. **Freeze** — Build global state snapshot
2. **Deliver** — Route emails to inboxes
3. **Observe** — Each agent reads from frozen snapshot
4. **Decide** — Each agent generates ActionPlan
5. **Act** — Execute actions through ToolRegistry
6. **Commit** — Atomic state update
7. **Audit** — Record all events

**Known limitation:** Observe phase passes a raw `dict` snapshot to agents. See §4.8 for concerns.

### 3.2 Agent Runtime Protocol (`agent_runtime.py`)

Defines the contract all agent implementations must satisfy:

```python
class AgentRuntime(Protocol):
    def observe(self, snapshot: dict) -> AgentObservation: ...
    def decide(self, observation: AgentObservation) -> ActionPlan: ...
    def act(self, plan: ActionPlan, context: ActionContext) -> list[ActionResult]: ...
```

**Built-in implementations:**
- `RootAgent` — restricted to {read, write, ls, delegate}
- `ManagerAgent` — can delegate + send_email
- `SubAgent` — base tools + extensible extras
- `BaseAgent` — subclassable default

**ToolContext (frozen dataclass):**
- Binds `agent_id` to every tool call
- Immutable — agents cannot modify their identity
- Created only by the system via `IdentityEnforcer`, never by agents

**ToolRegistry:**
- Central permission enforcement
- `authorize()` checks agent has tool permission
- `execute()` validates + runs handler
- Returns `ToolResult` on failure (permission errors returned, not raised)

### 3.3 Atomic Transaction Buffer (`transaction.py`)

Implements the Commit phase model from SPEC §8.2:

```
Act → stage effects → validate → resolve conflicts → commit/rollback
```

**StagedEffect lifecycle:**
```
STAGED → VALIDATED → COMMITTED
                  → FAILED (validation error)
COMMITTED → ROLLED_BACK (on partial failure)
```

**Conflict resolution (deterministic):**
- Same resource, same agent: keep by effect_id order
- Same resource, different agents: alphabetical by agent_id
- Lock holder wins over non-holder

**Known limitation:** Atomicity covers in-memory state only. External side effects (file writes, email delivery, lock persistence) are not part of the rollback boundary. See §4.12.

### 3.4 Identity Enforcement (`identity.py`)

Central service preventing identity spoofing:

```python
enforcer = IdentityEnforcer(tool_registry)
ctx = enforcer.create_tool_context("agent.research")  # system creates
email = enforcer.wrap_email_creation(ctx, to=["agent.root"], ...)  # system sets from_agent
enforcer.validate_sender(ctx, "agent.root")  # raises SpoofedSenderError
```

**Protections:**
- `ToolContext` frozen dataclass — immutable after creation
- `IdentityEnforcer` is the only place ToolContext is created
- Email `from_agent` set from context, not caller
- File/KB operations bound to context.agent_id
- Config modification prevention

**Known limitation:** Agents could theoretically call `IdentityEnforcer` directly if they import it. Defense is by design convention, not runtime isolation. See §4.10.

### 3.5 Email Sorting (Partial SPEC §13.3 Compliance)

Updated `_sort_key` in `mailbox.py`:

```python
def _sort_key(email: Email) -> tuple[int, int, int, str]:
    return (
        type_rank,          # 0=system_notice, 1=human_message, 2=other
        priority_rank,      # urgent=0, high=1, normal=2, low=3
```

**⚠️ Missing:** SPEC §13.3 also recommends sorting by task deadline. Current implementation does not incorporate `deadline_tick` into sort order. This is a known partial compliance.

### 4.6 AgentRuntime observe() Takes Plain dict

The current interface:

```python
def observe(self, snapshot: dict[str, Any]) -> AgentObservation: ...
```

Using a plain `dict` is problematic:
- No compile-time type safety for snapshot schema
- Agent could access unauthorized fields
- Snapshot schema evolution is uncontrolled
- Makes auditing and replay harder

**Recommended improvement:** Replace with a typed, read-only, per-agent filtered view:

```python
@dataclass(frozen=True)
class AgentSnapshot:
    tick: int
    agent_id: str
    emails: tuple[EmailView, ...]
    own_tasks: tuple[TaskView, ...]
    private_files: tuple[FileMetadata, ...]
    shared_resources: tuple[SharedResourceView, ...]
    held_locks: tuple[LockView, ...]
```

This is **not implemented** in v0.2.0 and should be a priority for v0.3.0.

### 4.7 Root Agent Restrictions

The `RootAgent` class restricts tools to `ROOT_TOOLS = frozenset({"read", "write", "ls", "delegate"})`:

| Question | Answer |
|----------|--------|
| Can Root call `send_email`? | **No** — not in ROOT_TOOLS |
| Can Root call `delegate`? | **Yes** — in ROOT_TOOLS |
| Can Root write to Shared KB? | **Only via delegate** — no direct Shared KB write tool |
| Can Root read sub-agent files? | **No** — PrivateStore enforces per-agent isolation |
| Can Root modify its own config? | **No** — IdentityEnforcer prevents config modification |
| Can Root create arbitrary email types? | **No** — only via delegate which generates delegation emails |
| Can Root directly change task state? | **Only via delegate** — DelegationProtocol manages task lifecycle |

**⚠️ Concern:** The `delegate` tool in RootAgent is a system capability that generates delegation emails. But the current implementation's `delegate` action simply calls `DelegationProtocol.delegate()`. If Root's `act()` method also has access to the `MailSystem` directly (via Simulation), there may be a bypass path. This needs runtime isolation verification.

### 4.8 ToolContext Source Verification

The `IdentityEnforcer` is the designated sole creator of `ToolContext`. However:

1. **Agent code could import `IdentityEnforcer` directly** — no runtime isolation prevents this
2. **`ToolContext` is a frozen dataclass, not cryptographically signed** — a forged instance could pass `isinstance` checks if constructed with the same fields
3. **No capability token** — ToolContext doesn't include a session-bound token
4. **Deserialized contexts are not verified** — if ToolContext were serialized/deserialized, provenance is lost

**Current protection:** Convention-based — agents are expected to only use `ToolFacade` provided by the system. This is adequate for controlled environments but not for adversarial settings.

### 4.9 ToolRegistry Error Semantics

Permission errors are returned as `ToolResult(success=False, error="...")` rather than raised as exceptions. This means:

- Agents must check `result.success` on every tool call
- Permission errors look identical to tool execution failures
- No distinct `error_code` field for programmatic handling
- Permission errors may be retried (wasteful) or silently ignored

**Recommendation:** Add `error_code: str` field (e.g., `"permission_denied"`, `"tool_error"`, `"not_found"`) and consider raising `ToolPermissionError` as a system-level exception that terminates the action plan.

### 4.10 Transaction Atomicity Boundaries

The `TransactionBuffer` stages in-memory `StagedEffect` objects. The "atomic commit" applies these to in-memory state:

```python
# Effects are applied to:
- Task tree states (in-memory)
- Email queue (in-memory)
- Shared KB resources (in-memory)
- Lock states (in-memory)
```

**NOT part of the atomic boundary:**
- Actual file system writes (PrivateStore)
- External service calls
- Audit log entries (append-only, always succeed)
- Lock lease timers (continue running)

**Known risk:** If the system crashes between "commit in-memory" and "persist to disk," state is lost. The transaction provides **logical atomicity within a single process lifecycle**, not durability.

### 4.11 Lock Token Mechanism

Current lock release: `release(resource, agent_id)` — only checks `owner_agent_id`.

**Stale-holder attack scenario:**
1. Agent A acquires lock on `resource.txt` at tick 5
2. Agent A's lease expires at tick 9
3. Agent B acquires lock on `resource.txt` at tick 10
4. Agent A's delayed `release()` call arrives — checks `owner_agent_id == "agent.a"` but the lock is now Agent B's

**Result:** Agent B's lock is incorrectly released.

**Fix needed:** Add `lock_token` to `LockInfo` and require it for `release()` and `renew()`. This is **P1 priority** — it affects correctness of concurrent access.

### 4.12 Email Delivery Timing Semantics

Currently, emails created during tick `t` have `deliver_at_tick = t + 1` (default). The sort key includes `created_at_tick`.

**Underspecified:**
- Can `deliver_at_tick` be set to `t` (same tick)?
- What happens if `deliver_at_tick < created_at_tick`?
- Can emails created in tick `t`'s Act phase be observed in tick `t`'s Observe phase? (They shouldn't be — Observe reads the frozen snapshot from the start of the tick)
- Does pausing affect delivery scheduling?

**Recommendation:** Formally specify: "All emails generated in tick `t` are earliest deliverable in tick `t+1`'s Deliver phase."

### 4.15 Deterministic Replay Scoping

The `DeterministicReplay` class provides in-memory snapshot storage and deterministic conflict ordering. Its guarantees are limited to:

- **Within-process, in-memory state** — not serialized
- **Fixed action inputs** — if the same ActionPlan is provided
- **Deterministic sorting** — conflict resolution by agent_id + effect_id
- **No external dependencies** — assumes no LLM, no random, no time, no network

**Cannot guarantee:**
- Cross-process replay
- LLM output replay
- File system state consistency
- Thread scheduling determinism

| Gap | Impact | Recommendation |

## 10. Recommendations for v0.3.0

All items below have been converted to KANBAN TODO entries in `KANBAN/TODO/` (21 items total, dated 2026-08-17).

### Priority P1 (Correctness)

1. **Lock Token Mechanism** — Add UUID-based lock tokens to prevent stale-holder attacks. Required before claiming "reliable concurrent access."

2. **Typed AgentSnapshot** — Replace `dict` in `AgentRuntime.observe()` with a typed, read-only, per-agent filtered dataclass. Prevents unauthorized data access and improves auditability.

3. **Transaction Boundary Clarification** — Document which operations are atomic (in-memory state) vs out-of-band (file writes, email delivery). Implement proper rollback for external side effects.

### Priority P2 (Completeness)

4. **Email Deadline Sorting** — Add `deadline_tick` to `_sort_key` for full SPEC §13.3 compliance.

5. **Email Delivery Timing Formalization** — Document: "tick `t` emails → tick `t+1` Deliver phase." Add boundary tests.

6. **Task Cancellation Propagation** — Implement cascade logic or explicit policy for parent→child task cancellation.

7. **True E2E Simulation Tests** — Write tests that drive `Simulation.run()` through the full tick cycle with `AgentRuntime.observe/decide/act`.

8. **Root Agent Runtime Isolation Test** — Verify Root cannot call `send_email` or access Shared KB directly.

9. **ToolRegistry Error Semantics** — Add `error_code` field to distinguish permission errors from tool execution failures.

10. **Conflict Resolution Refinement** — Non-lock-holder writes should fail directly; define merge/override/fail conflict types.

11. **SharedKB Double-Commit Path** — Eliminate direct `shared_kb.write()` path; enforce single transaction entry point.

12. **Timeout Phase Binding** — Bind timeout checks to specific tick phase (post-Commit, pre-Audit).

13. **Pause Semantics Documentation** — Document and test: lock leases and deadlines only advance with simulation ticks.

### Priority P3 (Infrastructure)

9. **CI/CD Pipeline** — GitHub Actions with Python 3.10/3.11/3.12 matrix.

10. **Test Coverage** — Add `pytest-cov`, report line/branch coverage.

11. **Static Analysis** — Add `mypy` + `ruff` to CI.

12. **LLM Agent Integration** — Implement concrete `AgentRuntime` with LLM calls in `decide()`.

13. **Cross-process Persistence** — JSON/SQLite serialization for simulation state.

## 11. Conclusion

My-Team v0.2.0 represents a **significant advancement** from v0.1.0:

| Aspect | v0.1.0 | v0.2.0 |
|--------|--------|--------|
| System integration | ❌ Standalone modules | ✅ `Simulation` class with 7-phase tick |
| Agent runtime | ❌ No runtime | ✅ `AgentRuntime` protocol + 4 implementations |
| Identity security | ❌ No enforcement | ⚠️ `IdentityEnforcer` + frozen `ToolContext` (convention-based) |
| Atomic commit | ❌ No transactions | ⚠️ `TransactionBuffer` (in-memory only) |
| Email sorting | ⚠️ Non-compliant | ⚠️ Partial §13.3 (no deadline sorting) |
| End-to-end tests | ❌ None | ⚠️ 8 protocol integration tests (not full simulation) |

**What v0.2.0 provides:** An integrated runtime foundation with simulation orchestration, agent lifecycle, tool authorization, email-based delegation, shared KB with permissions/locks/versions, transaction staging, and identity enforcement.

**What v0.2.0 does NOT provide:** Cross-process persistence, lock tokens, full deterministic replay, LLM agent reasoning, REST API, or verified end-to-end simulation runs.

**Status: Integrated runtime foundation — not yet complete SPEC conformance or production-ready.**

The next critical steps are:
1. Lock token mechanism (correctness)
2. Typed AgentSnapshot (security)
3. True E2E simulation tests (verification)
4. LLM Agent integration (functionality)
