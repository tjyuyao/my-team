## Executive Summary

v0.6.0 implements the **core async runtime**: the Tick kernel is
separated from the ReAct loop. Agents no longer block on LLM or tool
calls inside a tick — they submit Intents, enter waiting states, and are
re-activated when results arrive.

The design goal from the review:

> **ReAct is the agent's behavioral protocol; Tick is the kernel's advancement protocol. They are not 1:1.**

This is implemented and proven end-to-end with deterministic fake
providers:

```text
tick t:    Agent produces Intent (SubmitLLMRequest / SubmitToolRequest)
           → PendingOperationRegistry → WAITING_FOR_LLM / WAITING_FOR_TOOL
tick t+1:  FakeProvider completes op → Ingest delivers → agent re-activated
           → parses result → produces next Intent
```

**Scope honesty (per review):** this is a *prototype* runtime. Reliability
and safety boundaries are partially hardened in the post-review pass
(frozen snapshot reads, state-epoch fencing, timeout wake, budget) but
persistence (SQLite), crash recovery, real provider integration, and a
generic tool contract with sandboxing remain open — they are v0.7.0
targets, not v0.6.0 claims.

**Label:** `v0.6.0 — Async LLM/tool runtime prototype with continuation-based agents`

## What Changed

### 1. Agent decide() Produces Intents (`agent_runtime.py`, `llm_agent.py`)

**Before:** `decide(observation) -> ActionPlan` — rule-based agents
returned action lists; LLMAgent blocked on the model call inside the tick.

**After:** `decide_intents(observation, continuation) -> list[Intent]`

- `AgentRuntime` protocol extended with `decide_intents()`
- `BaseAgent.decide_intents()` default: converts `decide()`'s ActionPlan → Intents (backward-compatible bridge for rule-based agents)
- `action_plan_to_intents()` converter: delegate → DelegateIntent, send_email → SendEmailIntent, write → WritePrivateFileIntent, read/ls → SubmitToolRequest, complete_task → CompleteTaskIntent, fail_task → FailTaskIntent
- `LLMAgent.decide_intents()` **never blocks**:
  - Continuation has pending result → parse LLM response into Intents
  - Otherwise → `SubmitLLMRequest` (async)

### 2. Continuation-Based Agent State (`models/continuation.py`)

Each agent holds an `AgentContinuation` in `AgentRuntimeState`:

```text
phase: fresh | waiting_for_llm | waiting_for_tool | processing_result | ...
pending_request_id, react_turn, total_llm_calls, total_tool_calls
last_llm_result, last_tool_result
event_log (audit trail of the ReAct cycle)
```

Lifecycle across ticks:

```text
READY → PROCESSING → WAITING_FOR_LLM → (result arrives) → READY
→ PROCESSING → WAITING_FOR_TOOL → (result arrives) → READY → ...
```

Key additions:
- `receive_llm_result()` / `receive_tool_result()` — delivered by `_phase_ingest`
- `finalize_result_processing()` — resets phase after agent consumes a result
- `AgentRuntimeState.begin_activation()` — resumes WAITING_* agents → PROCESSING

### 3. Async External Operations (`pending_ops.py`)

`PendingOperationRegistry` tracks all in-flight external operations:

```text
SUBMITTED → PENDING → COMPLETED / FAILED / CANCELLED / TIMED_OUT
```

Each op: request_id, agent_id, task_id, created_tick, eligible_tick,
deadline_tick, status, result, error, retry_count.

**Critical fix:** consumed ops are `remove()`d after Ingest delivers them
— otherwise they re-deliver every tick, causing duplicate effects.

### 4. 10-Phase Kernel Tick Cycle (`simulation.py`)

Per the v0.6.0 review (方案 B), **Act is an explicit phase** between
Validate and Commit. The responsibility split is:

```text
Validate — Pre-Validate(Intent): may the agent even attempt this?
Act      — translate validated Intents into staged effects /
           registered pending operations (NO application)
Commit   — Commit-Validate(Effect/PendingOp) then apply;
           rollback + state-epoch bump on failure
```

```text
1. Ingest    — collect completed ops; fence stale/superseded results;
               wake timed-out agents with structured errors; deliver emails
2. Freeze    — snapshot global state incl. per-agent private file view
3. Schedule  — ready set from events + agent states
4. Observe   — ready agents read snapshot
5. Decide    — produce Intents (NON-BLOCKING, no sync LLM/tool)
6. Validate  — pre-validate Intents (tool capability, delegation, payload,
               LLM budget, duplicate request_id) — no side effects
7. Act       — translate Intents: stage effects, register pending ops
8. Commit    — commit-validate + apply staged effects; rollback on failure
9. Publish   — timeout checks, wake events
10. Audit    — record all events
```

Phase order is tracked per tick (`sim.last_tick_phases`) and verified by
`test_phase_order_includes_act`.

`_phase_act` converts validated Intents:

| Intent | Handling |
|--------|----------|
| SubmitLLMRequest | register LLM_REQUEST op, agent → WAITING_FOR_LLM |
| SubmitToolRequest (read/ls) | execute synchronously (local tools) |
| SubmitToolRequest (remote) | register TOOL_REQUEST op, agent → WAITING_FOR_TOOL |
| SendEmailIntent | stage EMAIL_SEND effect |
| DelegateIntent | stage TASK_CREATE + EMAIL_SEND effects |
| WritePrivateFileIntent | stage FILE_WRITE effect |
| CompleteTaskIntent / FailTaskIntent | stage TASK_UPDATE effect |
| WaitForEventIntent | agent → waiting state |

### 5. Deterministic Fake Providers (`fake_llm.py`, new)

- **`FakeLLMProvider`** — scripted LLM responses per (agent_id, call_index), configurable latency
  - `register_script()` / `replace_script()` (dynamic injection of runtime values)
- **`FakeToolExecutor`** — scripted tool results per (agent_id, tool_name)
- Both complete pending ops via `advance(sim, current_tick)` — the E2E harness
  calls this before each `sim.run_tick()`

### 6. Task Transition Walk (`task_tree.py`)

`update_status(allow_walk=True)` walks the transition graph when the
direct transition is invalid (e.g. `assigned → completed` goes through
`accepted → in_progress → submitted`). Strict by default; `_phase_commit`
uses the walk for TASK_UPDATE effects.

## P2: Transaction Hardening (post-P1)

### 7. SharedKB Single Write Entry (`shared_kb.py`, `simulation.py`)

**`SharedKB.write()` → `SharedKB._apply_committed()`** — the public
write method is now internal, callable only by the commit pipeline:

- Agents stage `KB_WRITE` effects via the `kb_write` tool handler
  (which carries `expected_version` and `lock_token`)
- `_phase_commit` validates permission/lock/version, then applies via
  `_apply_committed()` → version increments
- `KB_CREATE` / `KB_DELETE` effects also handled

**Latent bug fixed:** `LockManager` defines `__len__` (returns active
lock count), so `lock_manager or LockManager()` in `SharedKB.__init__`
replaced the valid *empty* manager with a fresh instance — SharedKB
and Simulation were using **different lock managers**. `_phase_commit`
permission checks passed (sim's manager) while `_apply_committed` saw
no lock (kb's manager) → write always failed. Fixed with explicit
`is not None` checks.

8 tests in `test_kb_e2e.py`: staged write commits, tool handler path,
rejections (no lock / wrong version / forged token), version
increments, internal apply still enforces checks.

### 8. Cross-Effect Commit Rollback (`simulation.py`)

`_phase_commit` now rolls back applied effects when application fails:

- Tracks created `email_ids` and `task_ids` during application
- On any apply failure (e.g. duplicate `TASK_CREATE`):
  - Removes created tasks and emails (reverse order)
  - Marks applied effects `ROLLED_BACK`, failing effect `FAILED`
  - Records `TRANSACTION_ROLLBACK` audit event
- Successful commits unaffected

4 tests in `test_commit_rollback.py`: rollback on task failure,
successful commit no-op, prior-tick state preserved, created task
removed on rollback.

## Post-Review Hardening (v0.6.0 final)

Applied from the v0.6.0 review (P0 + P1 items) + P3-11 persistence.
30 new tests across `test_phase_semantics.py`, `test_epoch_fencing.py`,
`test_snapshot_views.py`, `test_op_hardening.py`,
`test_persistence.py`, plus rollback completeness in
`test_commit_rollback.py`.

### 9. Act Restored as Explicit Phase

- `run_tick()` docstring and comments now list the 10-phase cycle;
  `sim.last_tick_phases` records the executed order
- Phase boundaries tested: Validate has no side effects; Act only
  stages/registers; Commit is the sole applier and only for validated
  intents (`test_phase_semantics.py`, 4 tests)

### 10. Frozen Snapshot Read View

- `_build_snapshot()` now captures a per-agent private file view
  (`private_files`: relative path → content, plus directory entries)
- `read`/`ls` in Phase 7 execute against this view via
  `ToolContext.read_view` — never the live filesystem. Writes staged
  in the same tick are invisible until Commit
- Same-tick reads see the frozen state; next-tick reads see committed
  content (`test_snapshot_views.py`)

### 11. State-Epoch Fencing

- `Simulation.state_epoch` increments on commit rollback (and any
  future restore); pending ops are stamped with the epoch at submission
- Ingest discards results whose epoch no longer matches
  (`epoch_mismatch`) or whose request the agent no longer waits on
  (`superseded`) — audited as `result.stale`, never delivered, never
  waking the agent
- `complete()` no longer resurrects terminal ops (CANCELLED / TIMED_OUT
  / FAILED)
- `test_epoch_fencing.py` (3 tests)

### 12. Timeout Wake + Agent-Driven Retry

- `timeout_expired()` now covers SUBMITTED ops (deadline applies from
  submission)
- Timed-out ops deliver a structured `{error, timed_out, request_id}`
  result to the waiting continuation and wake the agent — the agent
  decides retry / fail / escalate; a retry is a NEW request_id
- `test_op_hardening.py`: timeout wake, retry with new request id,
  LLM budget enforcement, duplicate request_id rejection (intra-plan
  and cross-tick), agent-scope isolation, cancelled-op late results

### 13. Rollback Completeness

- FILE_WRITE rollback restores previous content / removes newly
  created files
- Shared KB rollback restores resource content AND version metadata
- Rolled-back emails produce no NEW_EMAIL wake events
- Rollback bumps the state epoch (fences in-flight results)
- `test_commit_rollback.py` (2 new tests)

### 14. SQLite Persistence + Crash Recovery (`persistence.py`, P3-11)

`Simulation.save_to(path)` / `Simulation.load_from(path)`:

- **Store:** `SimulationStore` — SQLite, one transaction per save
  (all-or-nothing: a crash mid-save leaves the previous state intact),
  schema-versioned, corrupt/mismatched DBs fail cleanly
- **Saved:** config, agent tree, tick engine (tick + paused state),
  state epoch, tasks (+parent/owner maps), emails (all + pending +
  per-mailbox inbox/outbox), scheduler (wake conditions, queued
  events, activation history + counter), outbox entries, pending
  operations (incl. epoch stamps), shared KB (resources + versions +
  permission rules), locks (+counter), audit log (+event id counter),
  file-ops audit, agent runtime states (state machine + continuation)
- **Not saved:** runtime LOGIC (rebuilt by role from agent config;
  custom runtimes must be re-installed by the caller), provider
  script positions (external harness state — see OI-002), private
  workspace FILES (they live on disk under the saved base path)
- **Crash recovery proven:** pause → save → load (still paused,
  quarantined results intact) → resume → quarantined result ingested
- **Determinism proven:** a loaded sim runs in lockstep with the
  original — emails, audit event sequence, continuations, activations
  identical (test_deterministic_lockstep)
- 11 tests in `test_persistence.py`

## E2E Test Evidence

### Full Task Completion Roundtrip (`test_e2e_task_roundtrip.py`)

```text
tick 0:  human sends "analyze market" (deliver_at=1)
tick 1:  root wakes → SubmitLLMRequest → WAITING_FOR_LLM
tick 2:  LLM completes → root re-activated → parses delegate intent
         → task created + delegation email
tick 3:  research wakes (NEW_EMAIL) → SubmitLLMRequest → WAITING_FOR_LLM
tick 4:  LLM completes → research re-activated → writes report.md
         + sends [RESULT] email
tick 5:  root wakes ([RESULT] email) → SubmitLLMRequest → WAITING_FOR_LLM
tick 6:  LLM completes → root re-activated → completes task + replies to human
```

Verified at the end:
- Task status: **COMPLETED** (walked through intermediate states)
- Emails: delegation sent, result returned, human reply dispatched
- File: `report.md` written by research with LLM-derived content
- Agent states: both IDLE (no zombie waiting states)
- Audit log: ≥3 activations, ≥4 transaction commits

### Async Tool Flow (`test_e2e_async_tool.py`)

- Remote tool (web_search) → TOOL_REQUEST op → WAITING_FOR_TOOL
- FakeToolExecutor completes → agent re-activated → sends result email
- Tool timeout → TIMED_OUT
- Tool error → delivered to continuation
- **Hybrid flow**: LLM → tool → result (react_turn=2, 3-hop continuation)

## Known Limitations (honest list at final HEAD)

### Architecture

1. **Real LLM provider untested** — `llm_gateway.py` still at 51% (real litellm calls not exercised in CI)
2. **BoundedMicroLoop stale snapshot** — second round uses original snapshot, no re-observation
3. **AgentSnapshot still dict-based** — typed views (EmailView, TaskView, etc.) not yet implemented
4. **Frozen read view is in-memory only** — built per tick at Freeze; binary files are excluded; no versioned file history (content-addressable storage is a v0.7.0 design)
5. **Stale-epoch discards leave the agent waiting** — a fenced result does not wake the agent (per review: audit only); the agent stays in its wait state until a timeout/human intervention resolves it

### Transaction

6. **Save/load is at tick boundaries** — the transaction buffer is empty after each tick by design; a crash MID-tick loses the in-flight buffer (the previous committed state remains — this is the documented crash-recovery window)
7. **Rollback does not cover scheduler claims/activations** — a failed commit still completes the tick's activations (agents go idle; the failure surfaces via audit); a full snapshot-restore model is not implemented

### Async Semantics

8. **No cost/token budget** — per-agent LLM concurrency budget is enforced; token/cost caps per agent/task/simulation are not
9. **No provider 429/5xx handling** — retry is agent-driven after timeout errors; provider-level retry with backoff is not implemented
10. **Pause is cooperative, not preemptive** — external operations already in flight continue; pause gates scheduling and Ingest only

### Persistence

11. **Runtime logic is not persisted** — `load_from` rebuilds runtimes by role from agent config; custom runtimes (LLMAgent, test doubles) must be re-installed by the caller (documented in `load_from` docstring)
12. **Provider script positions are not persisted** — fake-provider harness state (OI-002); the lockstep test re-aligns scripts after load

### Resolved in this release (P1 + P2 + post-review hardening + P3)

- ✅ **SQLite persistence + crash recovery** — save/load all subsystem state atomically; pause → save → load → resume proven
- ✅ **Stale/superseded response rejection** — state-epoch fencing (`epoch_mismatch` / `superseded`), audited as `result.stale`
- ✅ **Timeout → wake with structured error** — agent decides retry/fail/escalate; retry creates a NEW request_id
- ✅ **Pause at commit boundary** — external results quarantined until resume
- ✅ **LLM budget** — per-agent max concurrent requests enforced in Validate
- ✅ **Duplicate request_id rejected** — intra-plan and cross-tick
- ✅ **Frozen snapshot reads** — read/ls execute against the Freeze view, never the live FS
- ✅ **File + KB rollback** — FILE_WRITE restores content; KB restores content + version; rolled-back emails produce no wake events; rollback bumps state epoch
- ✅ **SharedKB dual entry** — `write()` renamed to `_apply_committed()` (internal); all KB writes staged via TransactionBuffer
- ✅ **Cross-effect rollback** — `_phase_commit` rolls back applied effects on failure
- ✅ **Task+Email consistency** — rollback covers both: failed TASK_CREATE removes staged EMAIL_SEND and vice versa
